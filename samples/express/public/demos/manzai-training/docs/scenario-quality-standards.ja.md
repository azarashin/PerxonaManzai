# シナリオ品質基準

[English](scenario-quality-standards.md) | 日本語

## 1. 目的

この文書は、対話道場のシナリオをトレーニングに適したものにするための品質基準を定義する。JSON Schemaが
規定する構造上の制約と、[シナリオ生成ガイド](scenario-generation-guide.md)が規定する作業手順を補完する。

本基準は新規シナリオと、意図して改訂する既存シナリオに適用する。検査機能を変更するたびに、無関係な
既存シナリオまで同時に修正することは求めない。新しい規則をCIの必須条件にする前に、既存違反は別の
カタログ改善作業で解消する。

## 2. 情報源の役割

| 対象 | 正とする情報源 |
| --- | --- |
| JSONの構造、必須プロパティ、値域 | `../schemas/scenario.schema.json`と`../schemas/scenario-catalog.schema.json` |
| 生成手順と生成ツールに求める出力 | `scenario-generation-guide.md` |
| 品質の意図、レビュー基準、例外運用 | 本文書 |
| 機械判定する閾値と重大度 | [`scenario-quality-policy.json`](../config/scenario-quality-policy.json) |
| 実際の検査処理 | `../../../scripts/check-scenario-quality.mjs`と`../scenario-quality.js` |

これらが矛盾した場合は、都合のよい規則を選ばず矛盾自体を修正する。Schemaに適合していることは必要条件
だが、教育上有用であることの証明にはならない。

## 3. 重大度

| 重大度 | 意味 | 必要な対応 |
| --- | --- | --- |
| エラー | 決定的な規則への違反であり、シナリオを受け入れられない | 内容を修正するか、レビュー済みの例外を登録する |
| 警告 | 測定可能な危険パターンだが、意図的である可能性がある | 確認し、改善するか許容理由を記録する |
| 人手レビュー | 意味や安全性をJSONだけでは信頼して判定できない | 文脈を含めてレビューする |

検証を通すためだけに、生成ツールが閾値を緩和したり、エラーを警告へ変更したり、例外を追加したりしては
ならない。

## 4. 品質の基本原則

### 4.1 シナリオ固有性

すべての発話は、その場面、話者の意図、関係する事実に応答する必要がある。多くの無関係なシナリオへ
そのまま貼り付けられる文章は、通常は汎用的すぎる。

- その対話に登場する主張、懸念、矛盾、提案、判断対象を具体的に扱う。
- 講評では、その回答がもたらす具体的な結果を説明する。
- 保留や拒絶の定型句を埋め草として使い回さない。
- 挨拶や謝罪などの定型句は、役割が明確で、周囲の文章が場面固有なら使用できる。

### 4.2 選択肢の意味ある対比

選択肢は同じ回答の表面的な言い換えではなく、異なる会話戦略を表さなければならない。

- 最良の選択肢は、現在の文脈で学習対象の技能を実践する。
- 部分的な選択肢には、もっともらしい長所と、明確な不足またはリスクを持たせる。
- 弱い選択肢は現実的な失敗例とし、不正解にするためだけの荒唐無稽な回答にしない。
- 句読点、空白、丁寧語尾を除いても、発話として区別できる内容にする。
- aliasは現実的な同義発話に限り、二つの選択肢が同じ発話を認識しないようにする。

### 4.3 スコアの妥当性

配点から学習目標が読み取れるようにする。

- 各評価軸は、そのシナリオに関係する異なる技能を測定する。
- 評価軸の最大点は合計80点とし、完了点20点を加えて100点満点とする。
- 学習目標を完全に満たす回答には、内容点80点を与えられる。
- 部分的な回答は原則40〜70点とし、長所と不足の両方を説明する。
- 効果がない、安全でない、または誤った前提を受け入れる回答は原則0〜30点とする。
- 全選択肢を同点にしたり、順位に意味が生じない評価軸の値を付けたりしない。

### 4.4 カタログ全体の多様性

カタログでは、繰り返される定型回答の暗記ではなく、応用できる判断力を教える。

- 同一カテゴリの複数シナリオで、同じ正規化済み回答を最良の選択肢として再利用しない。
- カタログ全体で繰り返される表現は、設定された上限を超えないようにする。
- アバター発話、リアクション、講評を、名詞だけ差し替えたテンプレートとして使い回さない。
- 漫才の`なんでやねん。`のような汎用ツッコミは、作中の矛盾や誇張を明確に指している場合に限る。
  原則として、前提のどこがおかしいかを示す表現を優先する。
- カテゴリ上の慣例を、カタログ全体で同じ表現を繰り返す理由にしない。複数の有効な表現と戦略を教える。

### 4.5 翻訳品質

日本語、英語、繁体字中国語のすべてで、選択肢間の学習上の差を維持する。

- 語順ではなく、意図、丁寧さ、感情の強さ、業務上のリスクを翻訳する。
- 元言語では異なる選択肢を、翻訳先で同一の文にしない。
- 文化に依存する冗談、敬語、交渉慣行は、各言語で理解できる形にする。
- 各言語の講評は、同じ配点判断を説明する。

### 4.6 音声認識への適合

画面上の選択肢は音声入力として使われるため、認識可能な内容にする。

- 各言語の回答を、設定された文字数以下に保つ。
- 句読点や短い機能語だけで区別される選択肢を作らない。
- aliasは短く自然にし、同じ対話内では一つの選択肢だけに所属させる。
- 認識率を上げる目的で、広すぎる部分文字列をaliasに追加しない。

### 4.7 状態・分岐の品質

以前の選択が後の会話を実質的に変える場合だけ分岐を使用する。

- 状態変数は、信頼、緊張、提示可能な条件など、観察可能な学習上の結果を表す。
- 状態変化は選択内容に釣り合い、その後の対話から理由を理解できるようにする。
- 到達可能なすべての分岐に、有効な続行先または意図した終了を用意する。
- 対話、選択肢、結果が変わらないまますぐ合流する分岐を作らない。
- 状態が装飾にしかならない場合は、線形シナリオを維持する。

### 4.8 安全性と専門領域の境界

影響の大きい領域で、根拠のない断定を高く評価してはならない。

- 医療、法律、金融、本人確認、決済、アレルギー、安全、規制対象ポリシーでは、事実確認、上位者への
  引き継ぎ、または限定的な表現を優先する。
- 学習者に実在する個人情報を発話させない。
- 演習上必要な場合は、共感と責任の承認を明確に区別する。
- 強制、侮辱、差別、危険なエスカレーションを最良の戦略として扱わない。

## 5. 安定したルールID

診断結果と例外は安定したIDを使用し、違反理由を本文書から追跡できるようにする。

| ルールID | 既定の重大度 | 判定 | 要件 |
| --- | --- | --- | --- |
| `CHOICE_DUPLICATE_WITHIN_SCENARIO` | エラー | 機械 | 一つのシナリオ内で、正規化後の回答やaliasを異なる選択肢に所属させない |
| `CHOICE_REUSED_WITHIN_CATEGORY` | エラー | 機械 | 同一カテゴリの別シナリオで最良回答を再利用しない |
| `CHOICE_OVERUSED_ACROSS_CATALOG` | エラー | 機械 | 正規化後の回答がカタログ上限を超えない |
| `DIALOGUE_OVERUSED_ACROSS_CATALOG` | 警告 | 機械 | アバター発話がカタログ上限を超えない |
| `FEEDBACK_OVERUSED_ACROSS_CATALOG` | エラー | 機械 | 選択肢の講評がカタログ上限を超えない |
| `CHOICES_NOT_MEANINGFULLY_DISTINCT` | 人手レビュー | 人 | 翻訳後も異なる戦略を学べる選択肢にする |
| `SCORES_NOT_DIFFERENTIATED` | エラー | 機械 | 一つの対話の全選択肢を同じ合計点にしない |
| `SPEECH_CHOICE_TOO_LONG` | 警告 | 機械 | 発話文とaliasを設定された長さ以内にする |
| `MOTION_TAGS_NOT_VARIED` | 警告 | 機械 | 複数対話で理由なく同じリアクションパターンだけを使わない |
| `LOCALIZATION_INTENT_DRIFT` | 人手レビュー | 人 | 各言語で意図と配点理由を維持する |
| `BRANCH_STATE_NO_CONSEQUENCE` | 人手レビュー | 人 | 状態と分岐が演習内容を実質的に変えるようにする |
| `HIGH_IMPACT_UNVERIFIED_CLAIM` | 人手レビュー | 人 | 影響の大きい助言やポリシーを安全に扱う |

機械比較ではUnicode NFKC正規化、ロケールに依存しない小文字化、空白・句読点・記号の除去を行う。言語ごとに
比較し、日本語表現とその英訳を相互に重複判定することはしない。

既存シナリオの修正は品質基盤の変更範囲に含めないため、最初にcommitするポリシーは`audit`モードとする。
別の改善作業で既存カタログがエラー規則に合格してから、`enforce`へ切り替える。

## 6. 良い対比と悪い対比

### 漫才

使い回された弱い回答:

```text
なんでやねん。
```

場面固有の改善例:

```text
冷蔵庫に住んだら家賃より先に電気代で破産するわ！
```

改善例は誤った前提を特定し、その結果を誇張するという、別の場面にも応用できる技法を学習者へ示す。

### 接客

汎用的すぎる回答:

```text
分かりました。少し考えさせてください。
```

場面固有の改善例:

```text
提供時刻を確認します。その間に、すぐ用意できる料理へ変更することもできます。
```

改善例は事実確認と実行可能な代替案を組み合わせている。

## 7. 例外ポリシー

例外は、意図した製品要件または教育要件のために使用し、検証を簡単に通す目的では使用しない。

すべての例外に次の情報を含める。

- 一つのルールID
- 対象となる最小範囲のカテゴリ、シナリオ、対話、選択肢、言語、または表現
- 具体的な理由
- 安全性に関係する場合は担当者またはレビュー記録
- 一時的な例外の場合は有効期限または解消条件

表現単位またはシナリオ単位で指定できる例外を、カタログ全体に適用してはならない。通常は例外追加より
生成内容の修正を優先する。

## 8. 作成・レビュー手順

1. 対象カテゴリの指針と、同じカテゴリの複数シナリオを読む。
2. 最終的な台詞を書く前に、学習目標、評価軸、選択肢間の対比を設計する。
3. 各対話に固有の選択肢と講評を書く。
4. 日本語、英語、繁体字中国語で意図を個別にローカライズする。
5. Schema検証と品質検査を実行する。
6. すべてのエラーを解消し、すべての警告を確認する。
7. 本文書の人手レビュー項目を確認する。
8. 検証結果と承認済みの例外を報告する。

構造検証に成功し、自動品質検査が有効なポリシーを満たし、人手レビュー上の懸念が解消された時点で、
シナリオ生成を完了とする。

commit済みポリシーのモードでは`npm run quality:scenarios`を実行する。既存カタログを改善する作業では、
ポリシーを書き換えず将来のCI条件を確認するため`npm run quality:scenarios:enforce`を使用する。既存カタログを
別の変更で改善するまでは、厳格コマンドを通常のテスト処理に追加しない。合計だけが必要な場合は、どちらの
npmコマンドにも`-- --summary`を渡す。

## 9. 既存カタログの評価・改善手順

品質基盤の変更とシナリオ内容の変更は、別の作業として扱う。品質基盤を先にmergeし、更新された既定ブランチ
からシナリオ改善専用ブランチを作成する。別途レビューされたポリシー判断がない限り、改善ブランチでは閾値、
重大度、例外を変更しない。

### 9.1 ベースラインを記録する

内容を変更する前に、`samples/express`で次を実行する。

```text
npm run validate:scenarios
npm run quality:scenarios -- --summary
```

エラー数と警告数をタスクまたはPull Requestの記録に残す。これは各修正単位を比較する基準になる。改善によって
減少する値なので、ドキュメントへ固定値として記載しない。

個別の診断を確認する場合は、詳細コマンドを使用する。

```text
npm run quality:scenarios
```

PowerShellでは、ファイルを変更せずシナリオまたはルールに絞り込める。

```powershell
npm run quality:scenarios 2>&1 | Select-String "after-a-breakup"
npm run quality:scenarios 2>&1 | Select-String "CHOICE_DUPLICATE_WITHIN_SCENARIO"
```

### 9.2 小さな修正単位を選ぶ

一度に一つのカテゴリ、関係する小さなグループ、または一つのシナリオを改善する。多数のファイルに定型文が
ある場合は、原則として次の順に取り組む。

1. 汎用的な最良・部分的・弱い選択肢
2. 繰り返される講評
3. 繰り返されるアバター発話
4. 重複または範囲が広すぎるalias
5. 配点、翻訳、モーション、分岐上の問題

カタログ全体に対する類義語への一括置換は行わない。各修正は、シナリオの事実、話者の意図、学習者の役割、
学習目標に基づいて個別に作成する。

### 9.3 修正前に意味を評価する

各対話について次を整理する。

- 相手が何を主張し、感じ、または要求しているか
- 学習者が示すべき技能
- 各選択肢が表す異なる戦略
- 各戦略がその評価軸の点数になる理由
- 予想される会話上の結果
- 安全性、専門領域の境界、翻訳上のリスク

自動診断は測定可能な問題を示すが、回答が共感的、説得的、面白い、安全、または適切かを決定するものではない。
修正後の内容を採用する前に、本文書の人手レビュー基準を適用する。

### 9.4 修正してローカライズする

配点理由との整合性を保つため、選択肢と講評を一緒に修正する。逐語訳ではなく、日本語、英語、繁体字中国語の
すべてで戦略上の違いを維持する。表示する選択肢を確定してからaliasを再確認する。分岐シナリオの場合は、修正
した選択肢と状態変化が釣り合い、経路が一貫していることも確認する。

例外は汎用的な内容を書き直す代わりにはならない。例外が本当に必要な場合は、第7節で必要とされる根拠を付け、
別のポリシー変更として提案する。

### 9.5 修正単位ごとに検証する

各修正単位が終わるたびに次を実行する。

```text
npm run validate:scenarios
npm run quality:scenarios -- --summary
npm test
```

新しい合計を記録済みベースラインと比較し、変更したシナリオの詳細な診断も確認する。次を満たした時点でcommit
できる。

- 構造検証とテストに成功している
- 対象とした診断が解消している
- 文書化した理由なしにエラー数または警告数が増えていない
- 宣言した範囲外のシナリオを変更していない
- 人手レビュー項目を確認している

原則としてカテゴリまたはレビュー可能な修正単位ごとに一つのcommitとする。commitまたはPull Requestの記録に
修正前後の件数を記載する。

### 9.6 改善完了後にだけ厳格化する

すべての改善単位が完了したら、将来のゲートを確認する。

```text
npm run quality:scenarios:enforce -- --summary
```

エラーレベルの診断が一つでも残っている間、このコマンドは失敗する。成功後、別の品質基盤commitでポリシーを
`audit`から`enforce`へ変更し、厳格コマンドをCIへ追加してから、全テストを再実行する。

## 10. 改善を生成ツールへ依頼するテンプレート

Codex、Claude Codeなど、リポジトリを扱える生成ツールには次のように依頼する。

```text
<カテゴリまたはシナリオ>のシナリオ品質を評価し、改善してください。

編集前に、シナリオ生成ガイド、シナリオ品質基準、シナリオ品質ポリシー、
二つのシナリオJSON Schemaを読んでください。対象カテゴリの複数シナリオも確認してください。

制約:
- 最初に評価結果と修正案を報告する
- 宣言したシナリオまたはカテゴリの範囲だけを変更する
- 品質の閾値、重大度、例外を変更しない
- 繰り返された文章を表面的な類義語に置き換えるだけにしない
- 各選択肢を場面固有かつ意味の異なる戦略にする
- 講評と評価軸の配点を一致させる
- ja、en、zhで学習上の違いを維持する
- Schema検証、品質監査、テストを実行する
- 修正前後の診断件数と、残っている人手レビュー事項を報告する
```

評価だけを依頼する場合は、`この段階ではファイルを変更しないでください。`と追加する。内容変更を許可する
前に評価結果をレビューする。

## 11. 新規コンテンツを生成ツールへ依頼するテンプレート

利用前に山括弧内をすべて具体的な値へ置き換える。安全性、法令・業務上の制約、トーン、対象者は生成ツールに
推測させず明記する。

### 11.1 既存カテゴリへシナリオを追加する

```text
既存の<category-id>カテゴリへ新しいシナリオを一つ追加してください。

シナリオ要件:
- シナリオID: <scenario-id>
- 場面: <具体的な状況>
- 学習者の役割: <役割>
- アバターの役割: <役割>
- 対象者と難易度: <対象者と難易度>
- 学習目標: <観察可能な技能>
- 対話数: <件数>
- 安全性または専門領域の制約: <制約>

編集前に、シナリオ生成ガイド、シナリオ品質基準、シナリオ品質ポリシー、
発音ガイド作成手順、二つのシナリオJSON Schemaを読んでください。
scenarios/index.jsonの対象カテゴリ定義と、対象カテゴリの複数シナリオも確認してください。
既存の発話、選択肢、講評、aliasを複製してはいけません。

最初に、場面、評価軸、選択肢間の戦略上の対比、分岐方針を要約してください。
学習目標を大きく変える不明点がない限り、その後に実装まで進めてください。

制約:
- 新規シナリオファイルと、scenarios/index.jsonの登録に必要な箇所だけを変更する
- $schemaを保持し、一意なlowercase kebab-case IDを使用する
- カテゴリのbranching.requirementと多言語branching.rationaleに従う
- 以前の選択が後続へ影響しない場合は線形とし、分岐を使う場合は状態変化と経路によって後続対話を実質的に変える
- maxPointsの合計が80になる、場面固有で互いに異なる評価軸を定義する
- 各対話に、意味の異なる最良、部分的、弱いまたは危険な戦略を用意する
- 講評をaxisScoresと一致させ、その選択がもたらす結果を説明する
- ja、en、繁体字中国語zhで同じ学習上の違いを維持する
- すべてのbokeと選択肢textへpronunciationGuideを追加する。jaは全文ひらがな、
  enは/で囲んだ一般米語の広いIPA、zhは声調記号付き漢語拼音を使用する
- 選択肢を音声認識に適した長さと内容にし、aliasを狭く曖昧さのない表現にする
- 品質の閾値、重大度、例外、Schema、無関係なシナリオを変更しない
- 選択肢を劇的にするために安全性や専門領域の境界を弱めない

samples/expressで次を実行してください:
- npm run validate:scenarios
- npm run quality:scenarios -- --summary
- npm test

変更ファイル、カテゴリとシナリオID、対話数、分岐方針、配点方針、検証結果、
品質診断の変更前後の件数、残っている人手レビュー事項を報告してください。
明示的に依頼されていない限りcommitまたはpushを行わないでください。
```
