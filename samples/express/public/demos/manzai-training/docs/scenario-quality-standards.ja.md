# シナリオ品質基準

[English](scenario-quality-standards.md) | 日本語

## 1. 目的

この文書は、対話道場のシナリオをトレーニングに適したものにするための品質基準を定義する。JSON Schemaが
規定する構造上の制約と、[シナリオ生成ガイド](scenario-generation-guide.md)が規定する作業手順を補完する。

本基準は新規シナリオと、意図して改訂する既存シナリオに適用する。検査機能を変更するたびに、無関係な
既存シナリオまで同時に修正することは求めない。新しい規則をCIの必須条件にする前に、既存違反は別の
カタログ改善作業で解消する。

## 2. 情報源の役割

| 対象 | 正とする情報源 |
| --- | --- |
| JSONの構造、必須プロパティ、値域 | `../schemas/scenario.schema.json`と`../schemas/scenario-catalog.schema.json` |
| 生成手順と生成ツールに求める出力 | `scenario-generation-guide.md` |
| 品質の意図、レビュー基準、例外運用 | 本文書 |
| 機械判定する閾値と重大度 | シナリオ品質ポリシー |
| 実際の検査処理 | `../../../scripts/check-scenario-quality.mjs`と`../scenario-quality.js` |

これらが矛盾した場合は、都合のよい規則を選ばず矛盾自体を修正する。Schemaに適合していることは必要条件
だが、教育上有用であることの証明にはならない。

## 3. 重大度

| 重大度 | 意味 | 必要な対応 |
| --- | --- | --- |
| エラー | 決定的な規則への違反であり、シナリオを受け入れられない | 内容を修正するか、レビュー済みの例外を登録する |
| 警告 | 測定可能な危険パターンだが、意図的である可能性がある | 確認し、改善するか許容理由を記録する |
| 人手レビュー | 意味や安全性をJSONだけでは信頼して判定できない | 文脈を含めてレビューする |

検証を通すためだけに、生成ツールが閾値を緩和したり、エラーを警告へ変更したり、例外を追加したりしては
ならない。

## 4. 品質の基本原則

### 4.1 シナリオ固有性

すべての発話は、その場面、話者の意図、関係する事実に応答する必要がある。多くの無関係なシナリオへ
そのまま貼り付けられる文章は、通常は汎用的すぎる。

- その対話に登場する主張、懸念、矛盾、提案、判断対象を具体的に扱う。
- 講評では、その回答がもたらす具体的な結果を説明する。
- 保留や拒絶の定型句を埋め草として使い回さない。
- 挨拶や謝罪などの定型句は、役割が明確で、周囲の文章が場面固有なら使用できる。

### 4.2 選択肢の意味ある対比

選択肢は同じ回答の表面的な言い換えではなく、異なる会話戦略を表さなければならない。

- 最良の選択肢は、現在の文脈で学習対象の技能を実践する。
- 部分的な選択肢には、もっともらしい長所と、明確な不足またはリスクを持たせる。
- 弱い選択肢は現実的な失敗例とし、不正解にするためだけの荒唐無稽な回答にしない。
- 句読点、空白、丁寧語尾を除いても、発話として区別できる内容にする。
- aliasは現実的な同義発話に限り、二つの選択肢が同じ発話を認識しないようにする。

### 4.3 スコアの妥当性

配点から学習目標が読み取れるようにする。

- 各評価軸は、そのシナリオに関係する異なる技能を測定する。
- 評価軸の最大点は合計80点とし、完了点20点を加えて100点満点とする。
- 学習目標を完全に満たす回答には、内容点80点を与えられる。
- 部分的な回答は原則40〜70点とし、長所と不足の両方を説明する。
- 効果がない、安全でない、または誤った前提を受け入れる回答は原則0〜30点とする。
- 全選択肢を同点にしたり、順位に意味が生じない評価軸の値を付けたりしない。

### 4.4 カタログ全体の多様性

カタログでは、繰り返される定型回答の暗記ではなく、応用できる判断力を教える。

- 同一カテゴリの複数シナリオで、同じ正規化済み回答を最良の選択肢として再利用しない。
- カタログ全体で繰り返される表現は、設定された上限を超えないようにする。
- アバター発話、リアクション、講評を、名詞だけ差し替えたテンプレートとして使い回さない。
- 漫才の`なんでやねん。`のような汎用ツッコミは、作中の矛盾や誇張を明確に指している場合に限る。
  原則として、前提のどこがおかしいかを示す表現を優先する。
- カテゴリ上の慣例を、カタログ全体で同じ表現を繰り返す理由にしない。複数の有効な表現と戦略を教える。

### 4.5 翻訳品質

日本語、英語、繁体字中国語のすべてで、選択肢間の学習上の差を維持する。

- 語順ではなく、意図、丁寧さ、感情の強さ、業務上のリスクを翻訳する。
- 元言語では異なる選択肢を、翻訳先で同一の文にしない。
- 文化に依存する冗談、敬語、交渉慣行は、各言語で理解できる形にする。
- 各言語の講評は、同じ配点判断を説明する。

### 4.6 音声認識への適合

画面上の選択肢は音声入力として使われるため、認識可能な内容にする。

- 各言語の回答を、設定された文字数以下に保つ。
- 句読点や短い機能語だけで区別される選択肢を作らない。
- aliasは短く自然にし、同じ対話内では一つの選択肢だけに所属させる。
- 認識率を上げる目的で、広すぎる部分文字列をaliasに追加しない。

### 4.7 状態・分岐の品質

以前の選択が後の会話を実質的に変える場合だけ分岐を使用する。

- 状態変数は、信頼、緊張、提示可能な条件など、観察可能な学習上の結果を表す。
- 状態変化は選択内容に釣り合い、その後の対話から理由を理解できるようにする。
- 到達可能なすべての分岐に、有効な続行先または意図した終了を用意する。
- 対話、選択肢、結果が変わらないまますぐ合流する分岐を作らない。
- 状態が装飾にしかならない場合は、線形シナリオを維持する。

### 4.8 安全性と専門領域の境界

影響の大きい領域で、根拠のない断定を高く評価してはならない。

- 医療、法律、金融、本人確認、決済、アレルギー、安全、規制対象ポリシーでは、事実確認、上位者への
  引き継ぎ、または限定的な表現を優先する。
- 学習者に実在する個人情報を発話させない。
- 演習上必要な場合は、共感と責任の承認を明確に区別する。
- 強制、侮辱、差別、危険なエスカレーションを最良の戦略として扱わない。

## 5. 安定したルールID

診断結果と例外は安定したIDを使用し、違反理由を本文書から追跡できるようにする。

| ルールID | 既定の重大度 | 判定 | 要件 |
| --- | --- | --- | --- |
| `CHOICE_DUPLICATE_WITHIN_SCENARIO` | エラー | 機械 | 一つのシナリオ内で、正規化後の回答やaliasを異なる選択肢に所属させない |
| `CHOICE_REUSED_WITHIN_CATEGORY` | エラー | 機械 | 同一カテゴリの別シナリオで最良回答を再利用しない |
| `CHOICE_OVERUSED_ACROSS_CATALOG` | エラー | 機械 | 正規化後の回答がカタログ上限を超えない |
| `DIALOGUE_OVERUSED_ACROSS_CATALOG` | 警告 | 機械 | アバター発話がカタログ上限を超えない |
| `FEEDBACK_OVERUSED_ACROSS_CATALOG` | エラー | 機械 | 選択肢の講評がカタログ上限を超えない |
| `CHOICES_NOT_MEANINGFULLY_DISTINCT` | 人手レビュー | 人 | 翻訳後も異なる戦略を学べる選択肢にする |
| `SCORES_NOT_DIFFERENTIATED` | エラー | 機械 | 一つの対話の全選択肢を同じ合計点にしない |
| `SPEECH_CHOICE_TOO_LONG` | 警告 | 機械 | 発話文とaliasを設定された長さ以内にする |
| `MOTION_TAGS_NOT_VARIED` | 警告 | 機械 | 複数対話で理由なく同じリアクションパターンだけを使わない |
| `LOCALIZATION_INTENT_DRIFT` | 人手レビュー | 人 | 各言語で意図と配点理由を維持する |
| `BRANCH_STATE_NO_CONSEQUENCE` | 人手レビュー | 人 | 状態と分岐が演習内容を実質的に変えるようにする |
| `HIGH_IMPACT_UNVERIFIED_CLAIM` | 人手レビュー | 人 | 影響の大きい助言やポリシーを安全に扱う |

機械比較ではUnicode NFKC正規化、ロケールに依存しない小文字化、空白・句読点・記号の除去を行う。言語ごとに
比較し、日本語表現とその英訳を相互に重複判定することはしない。

## 6. 良い対比と悪い対比

### 漫才

使い回された弱い回答:

```text
なんでやねん。
```

場面固有の改善例:

```text
冷蔵庫に住んだら家賃より先に電気代で破産するわ！
```

改善例は誤った前提を特定し、その結果を誇張するという、別の場面にも応用できる技法を学習者へ示す。

### 接客

汎用的すぎる回答:

```text
分かりました。少し考えさせてください。
```

場面固有の改善例:

```text
提供時刻を確認します。その間に、すぐ用意できる料理へ変更することもできます。
```

改善例は事実確認と実行可能な代替案を組み合わせている。

## 7. 例外ポリシー

例外は、意図した製品要件または教育要件のために使用し、検証を簡単に通す目的では使用しない。

すべての例外に次の情報を含める。

- 一つのルールID
- 対象となる最小範囲のカテゴリ、シナリオ、対話、選択肢、言語、または表現
- 具体的な理由
- 安全性に関係する場合は担当者またはレビュー記録
- 一時的な例外の場合は有効期限または解消条件

表現単位またはシナリオ単位で指定できる例外を、カタログ全体に適用してはならない。通常は例外追加より
生成内容の修正を優先する。

## 8. 作成・レビュー手順

1. 対象カテゴリの指針と、同じカテゴリの複数シナリオを読む。
2. 最終的な台詞を書く前に、学習目標、評価軸、選択肢間の対比を設計する。
3. 各対話に固有の選択肢と講評を書く。
4. 日本語、英語、繁体字中国語で意図を個別にローカライズする。
5. Schema検証と品質検査を実行する。
6. すべてのエラーを解消し、すべての警告を確認する。
7. 本文書の人手レビュー項目を確認する。
8. 検証結果と承認済みの例外を報告する。

構造検証に成功し、自動品質検査が有効なポリシーを満たし、人手レビュー上の懸念が解消された時点で、
シナリオ生成を完了とする。
